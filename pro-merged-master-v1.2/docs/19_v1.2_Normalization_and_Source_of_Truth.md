## 2. v1.2 normative defaults

### 2.1 Frontend
Use React + Vite + TypeScript.
Rationale:
- the product is a local workbench, not an SSR or SEO site;
- FastAPI already owns the backend API surface;
- Vite reduces framework complexity for an agentic coder.

### 2.2 Queueing
Use `pipeline_jobs` as the durable application job ledger.
Use PGMQ as the preferred transport profile.
Use Redis/RQ/Dramatiq only if PGMQ packaging or operational compatibility blocks progress.
Redis is not part of the normative baseline runtime topology.

### 2.3 Auth and ACL
Use a household-aware baseline schema from day one.
Require DB-backed sessions.
Allow bootstrap password or magic-link setup for first local admin creation.
Recommend passkeys/WebAuthn before any non-local exposure.
Folder ACL is part of the baseline schema.
Implement bootstrap-password storage through a dedicated password-credential table using a strong one-way hash such as Argon2id.
Persist the session authentication method on each session row so `GET /api/v1/auth/session` can be answered from durable state.

### 2.4 Upload contract
The normative ingestion contract for browser and local API upload is `multipart/form-data` with a binary `file` part.
Base64 upload is not the primary contract.

### 2.5 Storage
Use a content-addressed filesystem object store on ZFS as the normative v1.2 baseline.
MinIO remains an optional later backend profile.

## 5. Implementation sequencing implication

Do not delay the auth/session API surface until the end. The full passkey UX can wait, but a clear session/login/logout contract cannot.
Do not delay household/ACL schema until “later multi-user work.” The tables and columns should exist in baseline migrations even if the first UI is single-household.
Treat bootstrap admin creation, password-credential storage, session issuance, and protected document routes as Phase 0 or early Phase 1 work, not late hardening.
