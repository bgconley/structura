# v1.3 normalization and design language

Prepared: 2026-04-23

This document is the current normalization layer for the Structura artifact pack. It supersedes older source-order notes where they conflict with this document, while preserving v1.2 decisions that are not explicitly changed here.

## 1. Normative source hierarchy

When files disagree, use this order:

1. `docs/10_Architectural_Decision_Record_Summary.md`
2. this file
3. `database/*.sql` in the documented apply order
4. `contracts/api/openapi.yaml`

9. the rest of the docs as explanatory context

Docs 13 through 20 remain useful rationale and change history, but they are not competing defaults.

## 2. Product identity

Structura is the canonical product namespace. Legacy pre-Structura naming must not be used in:

- product copy;
- example hosts;
- cookie names;
- queue names;
- object paths;
- service names;
- database comments;
- generated manifests or exports.

The application should describe itself as a local-first document workbench, not as generic document management, general storage, or a cloud document AI tool.

## 3. Data authority normalization

The system has three different kinds of truth, and implementation must keep them separate:

- original bytes: immutable source of truth for the document itself;
- structural artifacts: Docling JSON, pages, elements, chunks, previews, and model-run artifacts;
- accepted facts: canonical fields and canonical line items accepted by validation, policy, or human review.

For ordinary product behavior, `canonical_fields` and `canonical_line_items` are the default read model for:

- document detail fields;
- list filters;
- filing rules;
- exports;
- relationship suggestions;
- search enrichment;
- user-facing summaries of extracted facts.

Candidate tables remain essential, but they are review inputs, provenance records, and model comparison surfaces. They are not the accepted truth unless promoted into canonical facts.

Older extraction projection tables may remain useful for run history and raw outputs, but they should not compete with canonical accepted facts in UI or export paths.

## 4. Evidence normalization

Evidence for trusted extracted values must be concrete enough for a user to verify the claim. Page number alone is not sufficient.

A trusted evidence reference must include a page number plus at least one of:

- bounding box;
- element id;
- table id and row index;
- text span;
- source text excerpt.

The UI must make the evidence jump obvious and cheap. If a field cannot be traced to the source, it should be marked as suggested, unresolved, or review required rather than displayed as accepted.

## 5. Contract normalization

The OpenAPI contract is expected to cover the baseline product surfaces:

- auth session create/current/delete;
- document upload, inbox listing, and detail;
- protected asset access;
- field candidates and canonical field review actions;
- folders, tags, and document organization;
- relationships;
- contacts;
- filing rules;
- watched folders;
- search;
- analysis notes;
- exports;
- job and admin retry surfaces.

The API must not expose raw object-store URIs directly to the browser. Asset routes should authorize the caller, resolve the object internally, and stream or redirect through a controlled mechanism.

## 6. Storage normalization

Use separate ZFS-backed object areas for canonical originals, derived artifacts, and exports:

- `/srv/structura/objects/canonical`
- `/srv/structura/objects/derived`
- `/srv/structura/objects/exports`

Canonical originals are content-addressed and immutable after ingest. Derived artifacts may be regenerated, but their provenance should remain tied to a job, model, prompt, schema, or converter version where relevant. Exports are generated artifacts and should be auditable.

## 7. Design language thesis

The visual seed is `design-language-dashboard.PNG`. It establishes useful bones: left navigation, global search, operational badges, a document table, a right evidence inspector, and pipeline state. v1.3 should preserve that workbench density but change the center of gravity.

The design language is: calm evidence workbench.

Structura should feel like a serious private archive where the user can quickly answer:

- what needs my attention;
- what did the system extract;
- why does the system believe it;
- where is the source evidence;
- what action should I take next.

It should not feel like a generic analytics dashboard. Metrics exist to support document work; they are not the product's main story.

## 8. Product surface priority

Primary surfaces:

1. Inbox
2. Review Queue
3. Search
4. Document Detail
5. Evidence Inspector
6. Filing and Organization

Secondary surfaces:

- relationships;
- timelines;
- analysis;
- exports;
- admin and machine health.

Home should not default to a broad "Document Operations" dashboard. Prefer an Inbox or Review surface that includes compact operational context.

## 9. Layout system

Default desktop shell:

- left navigation: 176 px fixed;
- top bar: global search, upload, import, trust/health badges, user menu;
- main work area: list, review queue, search results, or document viewer;
- right inspector: selected document, extracted fields, evidence, related documents, actions;
- bottom pipeline strip: collapsed by default or scoped to selected document;
- admin health panel: available but visually quiet.

The right inspector should be persistent on desktop and collapsible on narrow screens. On mobile or tablet widths, inspector content should become a details drawer or dedicated tab rather than squeezing the evidence surface into an unreadable column.

## 10. Navigation language

Use user-task labels:

- Inbox
- Search
- Folders
- Review
- Relationships
- Timeline
- Analysis
- Exports
- Settings

Avoid overly internal labels as primary navigation. Pipeline, model runs, job ledgers, and queue internals belong in admin surfaces or contextual debug panels.

## 11. Visual tokens

### Color

Base:

- canvas: `#F7F9FC`
- panel: `#FFFFFF`
- raised panel: `#FBFCFE`
- border: `#D8DEE8`
- subtle border: `#E7ECF3`
- text: `#182235`
- muted text: `#64748B`
- faint text: `#94A3B8`

Actions and semantic states:

- primary blue: `#2563EB`
- primary blue hover: `#1D4ED8`
- focus ring: `#93C5FD`
- trust green: `#0F766E`
- review amber: `#C2410C`
- warning yellow: `#B45309`
- critical red: `#B91C1C`
- relationship violet: `#6D5BD0`

Use semantic colors sparingly. The dominant read should be paper, ink, line, and precise status accents, not a blue or purple theme.

### Type

- font family: Inter or system UI stack;
- body size: 13-14 px;
- table size: 12-13 px;
- headings: 16-22 px depending on surface;
- tabular numbers for counts, currency, confidence, dates, and job metrics;
- letter spacing: 0.

Do not use hero-scale typography inside the workbench. Dense operational UI needs compact but readable hierarchy.

### Radius and stroke

- controls and repeated item cards: 6-8 px radius;
- tables and panels: 8 px radius maximum;
- document thumbnails: 4 px radius;
- borders: 1 px;
- selected row: soft fill plus left or inline status emphasis, not a heavy outline.

## 12. Component guidance

### Document table

The document table is the primary scanning surface. Required columns for the default Inbox/Review view:

- selection;
- thumbnail;
- document name and stable id;
- family;
- counterparty;
- date;
- key amount or obligation;
- folder;
- review state;
- confidence;
- pipeline state;
- related count.

The table should support saved filters, keyboard row movement, and bulk actions without moving the user away from the selected document context.

### Evidence inspector

The inspector should show:

- document identity;
- family and short description;
- review state and confidence;
- page preview or viewer crop;
- extracted canonical fields;
- candidate/confidence details where relevant;
- explicit evidence jump controls;
- actions: accept, edit, mark reviewed, re-run extraction, link related document, file document.

The evidence jump should be more important than confidence percentage. Confidence without source visibility is not trustworthy enough for this product.

### Status chips

Use compact chips for:

- reviewed;
- needs review;
- low confidence;
- extracted;
- indexed;
- failed;
- duplicate suspect;
- unfiled.

Chips must include accessible text and should not rely on color alone.

### Pipeline strip

Show pipeline state as a contextual strip, not as the page's main content. The strip should answer whether a document is still processing, stale, failed, or fully indexed. Detailed job logs belong behind a drill-in.

### Search

Global search should remain persistent. It should search across lexical content, canonical fields, tags, folders, counterparty, and related-document context. Advanced filters should be available without crowding the main list.

## 13. Interaction principles

- default to fast scanning;
- keep selected document context stable while filters change;
- make review actions reversible or auditable;
- show machine uncertainty as work to resolve, not as decoration;
- make source evidence one click away;
- preserve keyboard access for high-volume review;
- keep admin and debug state visible enough to trust the machine, but quiet enough not to dominate the document workflow.

## 14. Responsive behavior

Desktop:

- persistent left nav;
- persistent right inspector;
- table/list plus details pattern;
- compact bottom pipeline strip.

Tablet:

- collapsible nav;
- inspector becomes a drawer;
- table columns reduce to the highest-signal fields.

Mobile:

- bottom navigation or compact top navigation;
- cards replace dense tables;
- evidence view becomes a separate step with clear return path;
- bulk operations become explicit selection mode.

## 15. Empty, loading, and failure states

Empty states should be practical and action-oriented:

- no inbox documents: upload or import;
- no review items: show recent reviewed documents and pipeline freshness;
- no search results: preserve filters and suggest which filters are active;
- failed extraction: show retry, open document, and review raw text if available.

Avoid marketing-style empty state copy. The product is a tool, not a campaign page.

## 16. Design artifact

The root `design-language-v1.3.html` file is a static visual reference for this direction. It is not an implementation requirement, but it captures the intended density, token usage, and product emphasis for the first React/Vite build.
