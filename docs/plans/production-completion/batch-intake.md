# UI-04 batch intake and processing observations — proposed next slices

Status: accepted execution design under the production completion plan. Implementation starts by separating the existing intake service's request models, file validation, record persistence and queue creation into cohesive owners. That refactor preserves the existing API, immutable storage transaction, cleanup and legacy job behavior; its database gate is pending. Upload-attempt persistence, stronger replay/duplicate semantics and batch UI are not implemented yet. This continues the integrated server-backed Inbox browse work and does not close the full UI-04 lifecycle package.

## Scope and source requirements

Deliver multi-file picker and drop intake, bounded concurrent transfers, per-file acceptance/failure and safe retry, an explicit exact-duplicate decision, and truthful document-scoped processing observations. Preserve the active route and selected document while background work changes. Keep bulk filing/selection, trash/restore, source deletion, email/ZIP, resumable chunk transport and native parser activation separate.

Inputs: [root plan Phase 1A–1D](../../../STRUCTURA_IMPLEMENTATION_PLAN.md), [product UI-04](product.md), [app specification §§6.1 and 7.2–7.3](../../../pro-merged-master-v1.2/docs/01_App_Specification.md), [stories 1.1–1.3 and 3.1](../../../pro-merged-master-v1.2/docs/04_User_Stories_and_Acceptance_Criteria.md), [normalization/design §§9, 12–15](../../../pro-merged-master-v1.2/docs/21_v1.3_Normalization_and_Design_Language.md), and [UI QA Inbox requirements](../../../STRUCTURA_UI_FIGMA_QA_PLAN.md). Use existing frame `17:2`, its local reference, and the documented narrow-screen drawer/tab pattern. Upload results belong in a compact expandable queue; processing belongs in a contextual strip, with detailed job logs remaining an operator concern.

## Slice A — durable per-file upload attempts

Recommended boundary: introduce a small upload-attempt resource before adding automatic transfer retries or duplicate reuse. Keep `POST /documents` backward compatible for current API/CLI/watcher callers; the new browser flow uses the stronger resource. Refactor its shared acceptance implementation rather than maintaining two document/original/job creation paths. The [concrete admission supplement](upload-attempt-contract.md) reserves migration 104 and refines transport, credential lifetime and transfer-storage accounting.

Proposed contract for review:

| Endpoint | Behavior |
| --- | --- |
| `POST /api/v1/uploads` | Create/recover an attempt using a client-generated operation UUID and immutable filename, declared size/type and source. Scope uniqueness to authenticated household and actor. Same key/metadata returns the same attempt; changed metadata conflicts. No document is created yet. |
| `PUT /api/v1/uploads/{uploadId}/content` | Transfer raw file bytes after metadata registration and pre-body admission. Validate actual bytes, stage/hash outside a DB transaction, then either atomically accept it or hold it for a duplicate choice. Replaying identical accepted content returns the original receipt without another document/job. |
| `GET /api/v1/uploads/{uploadId}` | Reconcile a lost response, refresh or interrupted transfer. Return the attempt only to its authorized actor; accepted/reused document links are also checked against current document ACL. Missing/inaccessible attempts are indistinguishable. |
| `POST /api/v1/uploads/{uploadId}/decision` | With the exact attempt revision, choose `keep_separate` or `use_existing` plus an authorized matching document ID. Keep separate creates one new document; use existing references the existing document without changing its facts, filing or jobs. |
| `DELETE /api/v1/uploads/{uploadId}` | Cancel an unaccepted attempt. Return the resulting state; if acceptance won the transaction race, return the accepted receipt. Cancellation never deletes or cancels an accepted document's processing. |
| `GET /api/v1/upload-policy` | Report supported MIME/extensions, maximum file bytes, bounded queue/concurrency policy and whether the stronger upload workflow is available. Policy is server-owned, not an independently drifting UI constant. |

`UploadAttempt` should have `uploadId`, operation ID, immutable `revision`, state, filename/declared size, actual size/hash when verified, timestamps, an optional typed safe error, and an optional acceptance receipt. States distinguish `awaiting_content`, `receiving`, `awaiting_duplicate_decision`, `accepted`, `reused`, `rejected`, `cancelled` and `expired`. Client byte progress is separate from these persisted states.

For a newly accepted file, the receipt includes exact `documentId`, original `assetId`, ingest `jobId`, server `batchId`, acceptance time and actual SHA-256. Preserve `AcceptedDocumentUpload` compatibility on the existing endpoint. A reuse result has `documentId` and no invented new job or acceptance timestamp for the old document. Do not return “queued” merely to fit an old DTO.

Persistence requires a root-allocated migration for actor/household-bound upload attempts, unique operation keys, a request revision/transfer lease, receipt references and bounded staging metadata. Prefer a dedicated `lib/uploads/` domain/service/repository boundary. The existing `ingest_batches` table has no ownership columns; do not expose it as an authorization shortcut. Browser batch grouping can remain an actor-scoped correlation ID on attempts, without changing the meaning of existing historical batches.

Required invariants:

- A short transaction reserves a transfer lease; byte IO and hashing occur outside database locks. Acceptance re-locks and checks that exact lease/revision, cancellation state and live credential/household authority before committing document, asset, jobs and receipt together. A stale/revoked/expired transfer cannot publish. Root/security review the lock order against content-hash cleanup, existing document locks and job ancestry before implementation.
- Use the existing content-addressed storage and reference-aware cleanup. Serialize same-hash acceptance before querying duplicates, with current ACL filtering. Repeated attempts for the same operation return one receipt even after a crash after commit or before the response reaches the browser.
- Server-verified content hash plus immutable request metadata define replay equality. Filename and byte count alone are insufficient. Same operation with different bytes conflicts; do not silently accept a replacement file.
- Duplicate candidates expose only readable records, with limited safe title/date/ID information and a bounded result page. `use_existing` rechecks hash, original asset and live ACL under lock. Revocation yields safe unavailability; it does not silently choose another record or create a new one. If no readable match exists, accept normally without a hidden-match flag or count.
- During an exact-duplicate decision, no second document exists yet. “Keep separate” creates an independently filed record sharing immutable bytes where storage permits. “Use existing” does not delete, merge, refile or rerun anything. “Cancel upload” discards only this unaccepted attempt. Structural duplicate suggestions remain in the relationship/review workflow.
- Staging cleanup expires unused content using leased ownership; an active transfer cannot be collected. Expiring staged bytes must not erase accepted receipts or cancellation tombstones and allow old keys to produce duplicate records. Cleanup retention and crash recovery need explicit storage-owner acceptance.
- The UI can cancel a not-yet-started file immediately. Aborting an HTTP transfer means delivery stopped, not proof that acceptance was cancelled. For an in-flight file, abort transport, request cancellation, then reconcile the attempt; display “Checking upload outcome” until accepted/cancelled is known. Loss of authentication clears private UI and stops transfers; reconciliation after sign-in uses the same actor-bound attempt identity.

Errors should be typed and safe: invalid content/empty/unsupported format (`415`/`422`), oversize (`413`), stale decision or changed replay (`409`), unauthenticated (`401`), unauthorized (`403` or safe missing-resource `404`), admission limit (`429` with `Retry-After`), temporary storage/service failure (`503`), and indeterminate network outcome. A definite rejection is not acceptance; an indeterminate outcome must be reconciled before any new operation key is allocated.

Client defaults proposed for validation: two active transfers and a bounded queue of 100 file references; use server policy to lower these values. Never read all file bytes into JS memory or hash the whole batch eagerly. Respect `Retry-After`, stop dispatch while offline, and allow only a small configured retry budget with jitter after idempotency is established. Server-side leased admission must apply across tabs/processes, bound temporary bytes and reject excess work before consuming the entire body. Queue wait is neither model failure nor a fabricated percentage. Do not reject otherwise safe file acceptance just because Qwen/embedding workers are unavailable.

## Slice B — accessible batch/drop UI

Depends on Slice A's replay/cancellation/error contracts. Replace the root's single pending boolean with a cohesive queue hook and reducer, not another orchestration block in `AuthenticatedApp`.

- One top-bar Upload control selects multiple supported files. An explicit Bulk Import entry opens the same queue with multi-file guidance; it is not a separate ingestion implementation. A keyboard-accessible drop area accepts files, reports directory/unsupported items per item and never navigates the browser to a dropped document.
- Each row has its own local queue ID, operation ID, filename/size, transfer progress, persisted attempt state and exact receipt. Show counts of queued/transferring/decision-needed/accepted/reused/rejected/cancelled items. Partial failure never becomes an undifferentiated “batch succeeded.”
- Use a dedicated XMLHttpRequest transport adapter for real upload-byte events; `fetchJson` does not expose upload progress. It must reuse session lifetime, configured CSRF cookie, credentials, safe error handling, abort and late-session response guards. A transfer reaching 100% changes to “Saving” until the receipt arrives; it does not claim processing completion.
- Retries keep the same operation/attempt identity; accepted files are never resent by “Retry failed.” Duplicate filenames remain separate entries. Re-selecting a file to resume an expired transfer checks its server-bound metadata/hash before acceptance.
- Acceptance refreshes the Inbox data and makes each exact document reachable within the two-second target after successful server completion. Multi-file acceptance does not repeatedly navigate or replace selection. The compact global queue offers “Open document”; a one-file action can preserve the current explicitly guarded navigation behavior. Filtering must not hide the fact that a file was accepted.
- Closing the queue collapses it; it does not cancel work. Show an accessible running-count control. If browser refresh would discard untransferred `File` objects, disclose it; restore persisted outcomes by operation IDs and request re-selection for remaining bytes. Do not store source bytes in localStorage or imply offline/background-upload support.
- Keep queue state inside the authenticated boundary. Keyboard focus enters and leaves the queue predictably; per-file actions have filename-specific accessible names, progress has an accessible label, live announcements are throttled, and Escape closes a modal drawer without cancelling uploads. At 390 px use the documented full-width drawer/tab pattern; preserve 176 px desktop rail and 56 px header.

## Slice C — actual processing observations, independent of batch scheduling

Add an ACL-safe read projection before the UI presents a pipeline summary. A proposed `POST /api/v1/documents/processing-status` takes at most 200 unique document IDs and returns observations only for readable documents; an exact `GET /documents/{id}/processing-status` supplies a selected-document strip. The collection read is bounded and avoids one polling request per visible row. It must not route through admin job listing or parse-debug APIs.

The DTO separates:

1. Document identity and `observedAt`.
2. Observed active work: bounded job IDs/stage labels, real queued/running/retry-scheduled states, safe failure code/reference, attempt counts and next attempt time where actually recorded. Use valid current ancestry and omit lineage-revoked work from active counts. A failed job awaiting a scheduled retry is not terminal `pipeline_failed`.
3. Published availability: protected original presence, actual source-rendered versus placeholder previews, current published parse/text availability, and explicit review/quality outcomes from their owning current read models. A completed worker is not evidence that every page was parsed or every index is current.
4. Observation limitations and action capability. No recorded work means “No current work observed,” not “Fully processed.” Missing observation is not zero work or healthy service. Quality outcomes `needs_human_review`, `insufficient_signal` and `no_extraction_target` stay distinct from operational failure.

Legacy jobs do not have a coherent document-wide generation selector. Do not pick the newest job across all types, allow old terminal failures to permanently poison a new result, or call a succeeded ingest job “Complete.” Show active work and explicitly scoped recent stage outcomes; report complete publication only when the owning publication contract establishes it. Root must approve this current/historical selection policy before wiring a single headline status. Candidate-native jobs/run/index states remain excluded from ordinary published-readiness claims; future native activation must extend this same projection under root's versioned publication contract.

Keep projection SQL in `processing_status_repository.py` with authorization and data read in one read-only snapshot; pure stage/outcome reduction belongs in `processing_status.py`. Share existing public diagnostic functions. Do not reuse the Phase 9 intake helper as a generic processing state machine: its absent-job fallback can return completed and its responsibilities include analysis eligibility.

Poll only visible Inbox IDs, current selection and newly accepted receipts; deduplicate IDs and requests, cancel on route/session change, and retain request-key guards. Proposed initial policy is a two-second interval while work is active, backing off after terminal observations/outages, with hidden-tab suspension and explicit Refresh. Validate the request volume against a moderate corpus. A poll error shows stale/unavailable observation time without wiping existing filing edits, accepted receipts or selected source context.

Ordinary users can refresh, open the original or go to Review. Do not display a processing Cancel/Retry button backed by the operator route. A later authorized document-processing command service must define whole-run scope, reauthorize writes, preserve human facts and use current job/run fences before such actions can be enabled. Cancelling an upload attempt and cancelling accepted processing remain different operations.

## Required acceptance evidence

- Real PostgreSQL: same operation replay after commit/lost response returns identical IDs and one document/asset/job set; simultaneous transfer leases cannot double-publish; changed bytes conflict; rollback and expired staging leave no unreferenced original; cancellation races produce exactly accepted or cancelled with no false success.
- Duplicate DB matrix: same bytes already readable, unreadable within household, other household, simultaneous copies, revoked match during decision, reuse versus keep-separate, stale decision revision. No hidden count/title/hash-existence signal; no source or accepted-fact mutation on reuse.
- Upload validation through the actual proxy/API: PDF, scanned PDF, PNG/JPEG/TIFF/WebP; zero/over-limit/mismatched/malformed files, omitted Content-Length, multipart overhead and interrupted stream; server admission limits hold across multiple tabs. Real image preview remains separately measured and truthfully represented.
- Browser: mixed 20-file batch with controlled delays, same-name files, per-file failures, retries and duplicates; maximum concurrent requests never exceeds policy; queue survives route changes, offers exact documents and retains active selection; same-file retry; all-queued cancellation; late acceptance after attempted cancel; offline, `429`, `503`, refresh, logout/session replacement and no old-account result publication.
- Processing DB/browser: independent ingest/preview/parse roots; ingest success while parse queued; partial fanout; scheduled retry versus dead letter; expired lease; revoked descendants; historical failure followed by successful work; hidden native sealed candidate; source-rendered versus placeholder previews; model unavailable with upload/manual filing still usable; ACL revocation and stale/out-of-order polling.
- Canonical Linux UI: 1440/1280 desktop and 390 mobile, keyboard-only drop alternative/queue actions, progress announcements, no page overflow, readable error/duplicate choices and unchanged source-return context. Review proposed screenshots individually.
- Measure accepted document visibility within two seconds after upload completion and common listing under 500 ms on the declared fixture; report actual values and remaining scope. Green mocked tests do not establish live model completion, full image-preview support, shared-service capacity or end-to-end parser publication.

Recommended implementation order: A contract/domain and meaningful DB cases; B transport/queue integration; C read projection in parallel after its selection policy is approved; then combined live upload/status evidence. Trash/restore and bulk document mutations begin only after these seams are stable.
