# Human correction contract

The UI-02 correction boundary validates the supplied JSON value before mutation on both canonical-field POST and `correct_field` review-action POST. Dates use valid `YYYY-MM-DD` strings and persist in `date_value`. Date/time values require RFC3339 with seconds, an explicit known UTC offset (`Z` or `±HH:MM`) and at most six fractional digits; they persist in `timestamp_value`. Historical datetime text rows remain readable. JSON values retain objects, arrays, scalars and explicit JSON null; non-finite numbers and unsupported values are rejected. Non-JSON null is not a generic clear operation: clearing a required typed fact still requires its own schema/review semantics.

`CanonicalField.updatedAt` is the exact database revision. Clients must retain every fractional digit and send it unchanged as `expectedUpdatedAt`, without passing it through JavaScript `Date`. Explicit null means the client loaded no canonical row at the selected field path and ordinal. The server checks that expectation after locking the document, before canonical/history/event mutation. A stale timestamp or unexpected existing row returns 409. A successful correction advances the revision by at least one microsecond. The request may retain its draft and reload the latest accepted fact to make a new decision.

Legacy clients that omit the expectation may create a new fact or make the first human correction to machine-only data. They cannot overwrite a fact that already has an accepted human actor: such requests return 409 and must reload a revision. The current web editor always sends an explicit expectation and disables correction if an existing canonical response lacks its revision. Supplied candidate identity must match the document, field path, ordinal and value type. Existing evidence/history shapes are retained.

All Review Queue actions share one pending-request guard. A task switch hides prior detail immediately; late responses cannot make another task's candidates actionable. Save failures retain form entries. Server-safe error details, including conflict instructions, are visible to the reviewer. The guard prevents overlapping submissions from this queue; it is not a durable idempotency ledger for every review action.

This slice does not claim all UI-02/UI-07 gates complete. Other workspaces need their own selection/concurrency audit; candidate acceptance/rejection and other task decisions need their remaining revision/idempotency semantics; a generic typed-null/clear operation and full schema-specific correction validation remain separate work. No history is rewritten and no migration is required.
